# Модель конкурентности

Практическое описание модели конкурентности (раздел 5 REQUIREMENTS.md — нормативный раздел,
это его пересказ для чтения без сверки с требованиями). Обоснование решений и рассмотренные
альтернативы — в [ADR-0003](adr/0003-concurrency-model.md), здесь не повторяются.

Реализация: `kvibe.KvibeStore`.

## Схема одной фразой

Один писатель, сериализованный явной блокировкой; сколько угодно читателей без блокировок,
опирающихся на инвариант «байты не меняются задним числом».

## Компоненты

- **Индекс (keydir)** — `ConcurrentHashMap<Key, Loc>`. `Key` — иммутабельная обёртка над
  `byte[]` с содержательными `equals`/`hashCode`; `Loc(offset, length)` указывает прямо на
  payload значения в файле.
- **`writeLock`** — один `ReentrantLock` на весь стор. `put`, `delete` и `close` берут его;
  `get` и `size` — нет.
- **`closed`** — `volatile`: читается lock-free другими потоками, значит без `volatile`
  видимость изменения из потока-писателя не гарантирована.
- **`poisoned`** — обычное поле: читается и пишется только внутри критической секции
  `writeLock` (см. [ADR-0004](adr/0004-durability-policy-and-poisoned-state.md)), поэтому
  дополнительная синхронизация ему не нужна.

## Ключевой инвариант

> Байты, единожды записанные по некоторому смещению, никогда не изменяются.

Из него следует безопасность чтения без блокировок: читатель, получивший `Loc` из индекса,
корректно прочитает данные по этому смещению, даже если конкретный ключ уже перезаписан или
удалён другим потоком (он просто увидит более раннюю версию — допустимый результат линеаризации
по ключу, но не между разными ключами).

**Инвариант нарушится сжатием (compaction, v0.2).** Переписывание файла с сохранением только
актуальных записей физически переместит байты, на которые указывают уже опубликованные `Loc`.
Схема чтения без блокировок в её нынешнем виде несовместима со сжатием — до его реализации
потребуется либо подсчёт ссылок на файл, либо копирование данных под защитой блокировки. Это
осознанный технический долг, а не забытая деталь.

## Порядок операций записи (нарушать нельзя)

1. Собрать буфер записи целиком в памяти (`RecordCodec.encode`).
2. Записать в файл по текущему смещению хвоста (`writeFully`).
3. При `SyncPolicy.EVERY_WRITE` — `channel.force(false)`.
4. Только теперь опубликовать `Loc` в `keydir`.

Публикация в `ConcurrentHashMap` устанавливает отношение happens-before: читатель, увидевший
новый `Loc`, гарантированно видит и записанные по нему байты — без этого читатель мог бы
получить смещение на данные, которые физически ещё не легли на диск.

## Гарантии

- Операции над **одним** ключом линеаризуемы.
- Между разными ключами атомарность не гарантируется — конкурентная запись двух разных ключей
  не имеет общего порядка, кроме того, что задаёт файловая сериализация writeLock'ом.
- Читатель никогда не наблюдает частично записанное значение.
- Поток, выполнивший `put`, немедленно после этого увидит своё значение в `get` (read-your-write
  в рамках потока).

Проверено тестом `KvibeStoreConcurrencyTest` (TR-5): пул виртуальных потоков, несколько
писателей с собственными ключами и монотонно растущим счётчиком, несколько читателей проверяют,
что счётчик по ключу не убывает во времени, плюс отдельная проверка `put`-затем-`get` внутри
потока-писателя.

## Известные ограничения (задокументированы, не устранены в 0.1)

- **`FileChannel` — `InterruptibleChannel`.** Если поток, читающий канал, будет прерван
  (`Thread.interrupt()`), канал закроется и станет непригоден для **всех** потоков, работающих
  с этим стором, а не только для прерванного. Вывод: не прерывайте потоки, работающие со
  стором. Корректная обработка (переоткрытие канала) — v0.2.
- **`close()` не ждёт конкурентные `get`/`size`.** Закрытие не блокируется в ожидании, пока
  читатели на других потоках завершат текущий вызов — вызывающий код отвечает за координацию
  жизненного цикла стора относительно своих читателей.
- **Poisoned state блокирует только запись, не чтение** — подробности и обоснование в
  [ADR-0004](adr/0004-durability-policy-and-poisoned-state.md).

## Память индекса (NFR-4)

Весь keydir постоянно живёт в куче — платит за каждый живой ключ:

- `Key`: объект-обёртка (заголовок объекта ~16 байт) + `byte[]` с собственным заголовком
  (~16 байт) и содержимым ключа.
- `Loc`: `record(long, int)` — компактный объект, порядка 24 байт с заголовком и выравниванием.
- Запись в `ConcurrentHashMap`: собственный узел (`Node`) поверх ключа/значения, порядка
  32-48 байт в зависимости от JVM и коллизий.

Итог — порядка **80-120 байт накладных расходов на ключ** сверх самих байт ключа, при типичных
коротких ключах (единицы-десятки байт). Практический предел: миллион ключей — это уже
десятки-сотни мегабайт только на индекс, до единого байта пользовательских значений (значения
на диске, не в памяти). Для больших объёмов ключей эта модель — сознательная граница
применимости 0.1, а не случайный недосмотр: подсчёт ссылок и постраничный индекс — вне
рамок учебного проекта.
