# Обзор архитектуры

Короткая карта кода — что где лежит и почему именно так. Для обоснования конкретных решений
см. ADR в `docs/adr/`; здесь — только структура и термины, без "почему выбрали X, а не Y".

## Три пакета, три ответственности

```
kvibe            — публичный API и оркестрация: KeyValueStore, KvibeStore, StoreConfig,
                   SyncPolicy, Key, Loc, StoreAlreadyOpenException.
kvibe.format     — кодек: перевод байты <-> структурированные данные, без файлового I/O.
kvibe.recovery   — восстановление индекса из файла при открытии стора.
```

`format` и `recovery` выделены отдельно от `kvibe` намеренно: это чистая, детерминированная
логика без обращений к диску напрямую (они получают уже прочитанные байты или `FileChannel`
для чтения, но не управляют жизненным циклом файла) — её легко и дёшево тестировать
исчерпывающе, поэтому именно на эти два пакета в TR-6 наложен повышенный порог покрытия
JaCoCo (80%), в отличие от остального кода.

## Что такое «кодек»

`RecordCodec` (и меньший `FileHeader`) в `kvibe.format` — это кодек в классическом смысле
coder/decoder: симметричная пара функций без побочных эффектов.

- `encode(timestamp, tombstone, key, value) → ByteBuffer` — собирает байты одной записи
  (CRC32C + заголовок + key + value) в памяти.
- `decode(ByteBuffer) → DecodedRecord` — разбирает байты обратно, с валидацией: проверяет
  длины key/value *до* аллокации массивов (TR-4) и проверяет CRC32C.

Кодек ничего не знает про файл или `FileChannel` — он не читает и не пишет на диск. Это
работа `KvibeStore` (запись/чтение по позиции) и `Recovery` (последовательный проход по уже
открытому каналу).

## Путь данных: `put`

```
KvibeStore.put(key, value)
    -> RecordCodec.encode(...)         // байты записи, в памяти
    -> writeFully(channel, buf, tail)  // позиционная запись на диск
    -> channel.force(...)              // по SyncPolicy
    -> keydir.put(key, Loc(offset, length))   // публикация в индекс — только после записи
```

`Loc(offset, length)` указывает прямо на payload значения (не на начало записи), поэтому
`get()` не перепарсивает запись целиком — читает `length` байт с `offset` напрямую.

## Путь данных: открытие стора (`open`)

```
KvibeStore.open(path, config)
    -> FileLock.tryLock()               // эксклюзивность процесса (FR-8)
    -> FileHeader: записать новый / прочитать и провалидировать существующий
    -> Recovery.scan(channel, afterHeader)
           -> последовательно RecordCodec.decode(...) по всем записям
           -> tombstone гасит более раннюю запись того же ключа
           -> первая невалидная/оборванная запись — точка усечения хвоста
    -> keydir восстановлен, tail = validTailOffset
```

## Ключевые типы одной строкой

| Тип | Роль |
|---|---|
| `KeyValueStore` | Публичный интерфейс (`put`/`get`/`delete`/`size`/`close`) |
| `KvibeStore` | Единственная реализация: writeLock на писателей, lock-free читатели |
| `Key` | Иммутабельная обёртка `byte[]` с содержательными `equals`/`hashCode` — ключ `ConcurrentHashMap`-индекса |
| `Loc` | `(offset, length)` — где лежит значение на диске |
| `RecordCodec` / `FileHeader` | Кодек: байты ↔ структура, без I/O |
| `Recovery` | Однократный проход по файлу → keydir + точка усечения хвоста |
| `StoreConfig` / `SyncPolicy` | Настройки долговечности (`force` на каждую запись или нет) |

Подробное обоснование каждого решения — в соответствующем ADR: модель Bitcask (0001),
формат записи и CRC32C (0002), модель конкурентности (0003), durability/poisoned state (0004),
отказ от `MappedByteBuffer`/FFM (0005).
