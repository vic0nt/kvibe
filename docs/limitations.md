# Известные ограничения (0.1)

Практический разбор: где именно и во что упрётся текущее решение при выходе за
сценарий, для которого оно спроектировано. Не дублирует нормативный раздел 1.3
REQUIREMENTS.md (не-цели) и известные ограничения из `docs/concurrency.md` —
собирает их вместе в одном месте с объяснением "во что конкретно упрётся".

## 1. Диск не возвращается — упрётся в место

Нет compaction: удалённые и перезаписанные значения остаются в файле мёртвым
весом навсегда. При интенсивном overwrite/delete одного и того же ключа файл
растёт линейно от числа операций, а не от числа живых ключей. Упрётся в
свободное место на диске быстрее, чем в теории нужно было бы.

## 2. Индекс целиком в RAM — упрётся в память по числу ключей, не по объёму данных

`ConcurrentHashMap<Key, Loc>` держит ~80-120 байт накладных расходов на ключ
(см. `docs/concurrency.md`, NFR-4). Миллион ключей — уже десятки-сотни МБ
только на индекс, независимо от размера значений (они на диске). Упрётся в
heap раньше, чем в диск, если ключей много, а значения маленькие.

## 3. Один писатель, сериализованный явной блокировкой — упрётся в throughput записи

`put`/`delete`/`close` идут строго последовательно через один `ReentrantLock`,
вне зависимости от числа CPU. При `SyncPolicy.EVERY_WRITE` это дополнительно
упирается в стоимость `fsync`: замер дал ≈120 оп/с против ≈19100 оп/с на
`NEVER` — разница ×160, целиком из-за `force()` (`docs/journal.md`). Упрётся в
write-throughput при конкурентной нагрузке от нескольких писателей
одновременно — параллелизма записи нет и не планировался.

## 4. Значение целиком в памяти при `get`/`put` — упрётся на больших значениях

Нет потоковой записи/чтения — значение читается и пишется одним куском
(`byte[]`). Значение, не помещающееся в память процесса, работать не будет —
это явная не-цель (раздел 1.3 REQUIREMENTS.md).

## 5. Один файл данных, без ротации — упрётся в лимиты одного файла/ФС при росте

Ротация нескольких файлов — только v0.3 по роадмапу (раздел 13
REQUIREMENTS.md). Пока один растущий файл — точка отказа и по месту, и
потенциально по времени восстановления при открытии (recovery читает его
целиком последовательно).

## 6. `FileChannel` — `InterruptibleChannel`, ловушка на прерывание потока

Если хоть один поток, читающий канал, получит `Thread.interrupt()`, канал
закроется для *всех* потоков этого стора, не только для прерванного. Упрётся
в неожиданный отказ всего стора там, где кто-то использует interrupt как
штатный механизм отмены (например, таймауты через `Future.cancel(true)`).

## 7. `close()` не ждёт читателей

Закрытие не блокируется, пока другие потоки читают — координация жизненного
цикла целиком на вызывающем коде. Упрётся в data race/`ClosedChannelException`
там, где закрытие и чтение не синхронизированы снаружи явно.

## 8. Poisoned state блокирует только запись

После неустранимой ошибки I/O писать нельзя (`IllegalStateException`), но
читать можно — по дизайну (ADR-0004), но это значит: приложение, которое не
проверяет состояние явно, может решить, что всё работает, потому что `get`
продолжает отвечать.

## 9. Единственный процесс — `FileLock` не защищает от многопроцессности иначе, чем отказом

Второй процесс, пытающийся открыть тот же файл, получит
`StoreAlreadyOpenException` — это не блокировка на запись между процессами в
духе БД, а просто «нельзя открыть дважды». Никакой межпроцессной координации,
реплик, кластера нет и не планируется (раздел 1.3 REQUIREMENTS.md).

## 10. Не-цели, зафиксированные явно — упрутся сразу, если понадобятся

Сетевой протокол, транзакции над несколькими ключами, репликация, диапазонные
запросы/сортировка ключей, TTL/вытеснение, шифрование, сжатие данных — ничего
этого нет и не появится в этой архитектуре без существенного переосмысления
(раздел 1.3 REQUIREMENTS.md).

## 11. Замер производительности — не то, на что можно полагаться как на гарантию

Baseline в `docs/journal.md` — один прогон, однопоточно, конкретное железо
(Apple M1 Pro, APFS, Temurin 25.0.1), явно не JMH (NFR-5 сознательно отложил
строгие замеры на v0.2). Это ориентир, не SLA — упрётся в неожиданные цифры на
другом железе/ФС (особенно не-APFS/Linux ext4, где `fsync` может стоить
иначе).

## Итог

KVibe 0.1 честно держит один сценарий — умеренное число ключей, умеренный
размер значений, один процесс, нагрузка без экстремальной конкуренции
писателей — и явно документирует, что выход за эти рамки (масштаб по ключам,
sustained heavy writes, отмена по interrupt, много процессов) не проверялся и
архитектурно не решён, а не «работает, просто медленно».
