# 0003. Модель конкурентности: один писатель, читатели без блокировок

Дата: 2026-07-27

## Статус

Accepted

## Контекст

NFR-2/NFR-3 требуют поддержки многих одновременных читателей, линеаризуемости операций над
одним ключом, отсутствия «рваных» (частично записанных) значений для читателя и гарантии
read-your-write в рамках одного потока. Нужна схема, которая одновременно достаточно проста,
чтобы её можно было полностью обосновать за отведённое время проекта (1.1), и по-настоящему
проверена под нагрузкой, а не просто описана в документе.

## Решение

- Индекс — `ConcurrentHashMap<Key, Loc>` (`kvibe.KvibeStore`).
- Все писатели (`put`, `delete`, `close`) сериализуются одним `ReentrantLock`
  (`writeLock`). Обоснование выбора `ReentrantLock` вместо `synchronized` уже зафиксировано в
  REQUIREMENTS.md, 5.1, и здесь не повторяется целиком: коротко — явный API (`tryLock`,
  `isLocked`) полезен для диагностики зависшего писателя, и корректность модели не должна
  зависеть от JVM-специфичного поведения пришпиливания виртуальных потоков (JEP 491), а не от
  гарантии JLS.
- Читатели (`get`, `size`) блокировку не берут вовсе — читают позиционно
  (`FileChannel.read(buffer, position)`), полагаясь на ключевой инвариант (5.2): «байты, единожды
  записанные по некоторому смещению, никогда не изменяются».
- Порядок операций записи (5.3) — буфер в памяти → запись → `force` по политике → публикация
  `Loc` в `keydir` — именно в этом порядке. Публикация в `ConcurrentHashMap` устанавливает
  happens-before: читатель, увидевший новый `Loc`, гарантированно видит и записанные по нему
  байты.
- `close()` тоже проходит через `writeLock` (хотя формально не «писатель» в смысле FR-1) — это
  не даёт `put`/`delete` начаться после того, как файл уже логически закрывается, и наоборот.

Проверено тестом `KvibeStoreConcurrencyTest` (TR-5): пул виртуальных потоков, несколько
писателей с собственными ключами и монотонно растущим счётчиком, несколько читателей проверяют,
что счётчик по ключу не убывает во времени в рамках одного потока-читателя, плюс отдельная
проверка `put`-затем-`get` в потоке-писателе. 10+ секунд под нагрузкой, ни одного исключения.

## Рассмотренные альтернативы

**Блокировка на каждый ключ (striped locks) вместо одной глобальной.** Отклонено. Append-only
модель Bitcask (ADR-0001) даёт ровно один физический ресурс, за который в любом случае надо
сериализоваться, — хвост файла. Блокировки по ключам не убрали бы эту точку сериализации, а
только добавили бы риск взаимной блокировки при будущих составных операциях и сложность без
измеренной выгоды (NFR-5 явно откладывает оптимизацию производительности).

**`ReentrantReadWriteLock` с читателями, участвующими в блокировке.** Отклонено. Позиционное
чтение уже потокобезопасно и не требует координации; ключевой инвариант 5.2 даёт безопасность
чтения без блокировок бесплатно. Read-lock добавил бы только конкуренцию без прироста
корректности.

**`synchronized` вместо `ReentrantLock`.** Отклонено — см. REQUIREMENTS.md, 5.1, полное
обоснование там же.

**Оптимистичная запись без единой блокировки** (например, резервирование хвоста через
`AtomicLong.getAndAdd`, дальше — независимая запись каждым писателем в свой зарезервированный
диапазон). Отклонено. Если несколько писателей резервируют смещения и пишут независимо, порядок
завершения физической записи на диск может не совпасть с порядком резервирования — тогда
публикация `Loc` в индекс должна дожидаться не только «своей» записи, но и знания, что все
более ранние по смещению записи тоже завершились (иначе читатель может получить `Loc` на байты,
которые физически ещё не легли на диск). Решаемо (watermark по непрерывно завершённым
смещениям), но это самостоятельный источник ошибок ради не измеренного выигрыша — не
соответствует приоритету 1.1 при отсутствии цели по производительности (NFR-5).

## Последствия

- Пропускная способность записи ограничена одним последовательным путём — осознанно, целей по
  производительности в 0.1 нет (NFR-5).
- Известная ловушка 5.4 (`FileChannel` — `InterruptibleChannel`: прерывание потока-читателя
  закрывает канал для всех) остаётся задокументированным ограничением 0.1, не устраняется здесь
  (переоткрытие канала — v0.2).
- Сжатие (compaction, v0.2) нарушит инвариант 5.2 «байты не меняются» — модель чтения без
  блокировок потребует пересмотра (подсчёт ссылок или копирование под защитой блокировки),
  это уже зафиксировано как OQ-2 и не решается этим ADR.
