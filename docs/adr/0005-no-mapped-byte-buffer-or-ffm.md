# 0005. Отказ от MappedByteBuffer и Foreign Function & Memory API в пользу FileChannel

Дата: 2026-07-27

## Статус

Accepted

## Контекст

Для файлового ввода-вывода в JVM есть несколько путей: обычный `FileChannel` с кучевыми
`ByteBuffer` (что уже используется во всём `kvibe.format`/`kvibe.recovery`/`kvibe.KvibeStore`),
`MappedByteBuffer` (файл, отображённый в память процесса), и Foreign Function & Memory API
(`java.lang.foreign`) как более новый низкоуровневый инструмент для внеочагового доступа к
памяти и файлам. Нужно явно решить, каким из них пользоваться, а не молчаливо прийти к смеси
всех трёх по ходу дела.

## Решение

Используем только `FileChannel` с обычными кучевыми `ByteBuffer` (`ByteBuffer.allocate(...)`).
`MappedByteBuffer` и `java.lang.foreign` (Arena/MemorySegment) не используются нигде в проекте.

Причины:
- **Детерминированное закрытие.** У `MappedByteBuffer` нет надёжного публичного способа
  размапить регион по требованию — отображение живёт до срабатывания сборщика мусора/Cleaner-а.
  Это прямо противоречит FR-6 (`close` ОБЯЗАН быть идемпотентным и детерминированным) и создаёт
  риски для FR-8 (`FileLock`): на части платформ незакрытое отображение мешает усечению
  (`truncate`) или удалению файла.
- **Простая и предсказуемая семантика `force`.** `FileChannel.force(boolean)` — ровно то, что
  нужно FR-7; смешивание позиционной записи через канал с параллельным memory-mapped
  отображением того же файла добавляет вопросы согласованности («когда именно отображение видит
  запись через канал»), разбираться в которых — не то, ради чего затевался этот проект (1.1
  — приоритет на durability и конкурентность, а не на нюансы взаимодействия mmap и каналов).
- **Позиционные операции уже потокобезопасны.** `FileChannel.read`/`write(buffer, position)`
  задокументированы как безопасные для конкурентного использования и не трогают общую позицию
  канала — это именно то, на чём построена модель чтений без блокировок (ADR-0003, 5.1).
- **FFM API — другая, более крупная область знаний.** `java.lang.foreign` наводит на
  собственную дисциплину владения памятью (`Arena`, время жизни `MemorySegment`), формально
  недавно стабилизировавшуюся. Изучать её — самостоятельная, отдельная от durability/
  конкурентности задача; она увела бы учебный фокус в сторону от того, что раздел 1.1 называет
  приоритетом.

## Рассмотренные альтернативы

**`MappedByteBuffer` для чтений** (чтобы не копировать данные в кучевой буфер). Отклонено по
причине детерминированного закрытия выше; выигрыш по скорости не измерялся и не является целью
0.1 (NFR-5).

**`MemorySegment.mapFile` (FFM) как замена mmap.** Отклонено по той же причине, что и
`MappedByteBuffer` — в основе всё то же отображение файла со схожей семантикой времени жизни,
плюс дополнительная стоимость освоения API.

**FFM только для внеочаговых буферов записи/чтения (без mmap, просто нативная память вместо
кучи, поверх обычного `FileChannel`).** Отклонено: значения и так копируются в/из кучевых
массивов на границе публичного API (`byte[]`, FR-2), поэтому внеочаговый буфер не убрал бы ни
одной копии для этого проекта — стоимость управления временем жизни `Arena` без всякой выгоды.
Отмечено как возможная идея для off-heap индекса (роадмап v0.4), но не для пути ввода-вывода
файла данных.

## Последствия

- Каждое чтение/запись проходит через кучевой `ByteBuffer`; файл никогда не отображается в
  память. Верхняя граница на размер одного значения и так — 16 МиБ (FR-2), так что отказ от
  mmap не создаёт дополнительных ограничений сверх уже существующих.
- Если производительность чтения на больших файлах когда-нибудь станет реально измеренным
  узким местом (после baseline-замера, NFR-5) — этот ADR потребует пересмотра/замены новым,
  а не тихой правки задним числом (раздел 9, правила ведения ADR).
