# KVibe — требования, версия 0.1

| | |
|---|---|
| **Статус** | Draft (зафиксировать коммитом до первой строки кода) |
| **Дата** | 2026-07-27 |
| **Цель релиза** | Работающее встраиваемое KV-хранилище, безопасное при многопоточном доступе, за 3-4 вечера |
| **Формат версий** | SemVer, до 1.0 обратная совместимость не гарантируется |

Ключевые слова **ОБЯЗАН** (MUST), **СЛЕДУЕТ** (SHOULD), **МОЖЕТ** (MAY) трактуются по RFC 2119.
Идентификаторы (`FR-1`, `NFR-3`, `TR-2`…) стабильны — на них ссылаемся из сообщений коммитов, ADR и заголовков тестов.

---

## 1. Цель и не-цели

### 1.1 Зачем этот проект

Проект **учебный**. Приоритет целей именно в этом порядке:

1. Разобраться на практике, что такое долговечность записи (`write` ≠ «на диске») и как это тестировать.
2. Спроектировать и обосновать модель конкурентности, а не «навесить `synchronized` и молиться».
3. Отработать дисциплину: property-based тесты, краш-тесты, ADR, документация.
4. Сдать домашку по вайб-кодингу 😁

Отсюда правило, действующее на весь проект: **если выбор стоит между «быстрее сделать» и «понятнее объяснить в ADR», выбираем второе.**

### 1.2 Что это такое

Встраиваемая (in-process) библиотека — хранилище пар «ключ-значение» с индексом в памяти и лог-структурированным файлом на диске. Модель — Bitcask (Basho, 2010). Библиотека называется KVibe (рубрика "Каламбуры за 300")

### 1.3 Не-цели

Сознательно **не** делаем ни в 0.1, ни в обозримом будущем: сетевой протокол и клиент-сервер, транзакции над несколькими ключами, репликацию и распределённость, диапазонные запросы и сортировку ключей, TTL и вытеснение, шифрование и сжатие, поддержку значений, не помещающихся в память.

Отложено на потом, но заложено в архитектуру: сжатие (compaction) (v0.2), несколько файлов данных с ротацией (v0.3), off-heap индекс (v0.4).

## 2. Глоссарий

| Термин | Значение |
|---|---|
| **Запись (record)** | Единица в файле: заголовок + ключ + значение |
| **Tombstone** | Запись-надгробие, отмечающая удаление ключа |
| **Индекс (keydir)** | Отображение «ключ → (смещение, длина)» в памяти |
| **Активный файл** | Единственный файл данных, в конец которого идёт запись (в 0.1 он же единственный) |
| **Огрызок (torn write)** | Неполная запись в хвосте файла после аварийного завершения |
| **Сжатие (compaction)** | Переписывание файла с сохранением только актуальных версий |
| **Poisoned state** | Состояние стора после неустранимой ошибки ввода-вывода, когда дальнейшая работа небезопасна |

## 3. Функциональные требования

**FR-1. Публичный API.** Библиотека ОБЯЗАНА предоставлять интерфейс:

```java
public interface KeyValueStore extends AutoCloseable {
    void put(byte[] key, byte[] value) throws IOException;
    byte[] get(byte[] key) throws IOException;   // null, если ключа нет
    boolean delete(byte[] key) throws IOException; // true, если ключ существовал
    int size();                                   // число живых ключей
    @Override void close() throws IOException;
}
```

Открытие — статической фабрикой: `KvibeStore.open(Path path, StoreConfig config)`.
Расширение API в 0.1 ЗАПРЕЩЕНО: никаких `putIfAbsent`, итераторов, батчей.

**FR-2. Семантика ключей и значений.**
- Ключи и значения — `byte[]`. `null` ЗАПРЕЩЁН, бросаем `NullPointerException` через `Objects.requireNonNull`.
- Массивы, переданные в `put`, ОБЯЗАНЫ копироваться при входе; массивы, возвращаемые из `get`, — принадлежат вызывающему. Вызывающий не должен иметь возможности испортить внутреннее состояние, изменив свой массив после вызова.
- Ограничения: ключ 1…65 535 байт, значение 0…16 МиБ. Нарушение → `IllegalArgumentException`.
- **Пустое значение (`new byte[0]`) — валидное значение и ОБЯЗАНО отличаться от отсутствия ключа.** Поэтому удаление помечается флагом в заголовке, а не нулевой длиной.

**FR-3. Персистентность и восстановление.** После корректного `close` и повторного `open` состояние ОБЯЗАНО совпадать с состоянием до закрытия. Индекс восстанавливается однократным последовательным проходом по файлу.

**FR-4. Удаление.** Дописывает tombstone и удаляет ключ из индекса. Место в файле не освобождается — это задача сжатия (v0.2).

**FR-5. Целостность.** Каждая запись ОБЯЗАНА содержать CRC32C. При открытии файл читается до первой записи с несовпавшей контрольной суммой либо до обрыва; хвост после этой точки ОБЯЗАН быть отброшен усечением файла (`FileChannel.truncate`).

**FR-6. Жизненный цикл.** `close` идемпотентен. Любая операция после `close` ОБЯЗАНА бросать `IllegalStateException`. Стор реализует `AutoCloseable`.

**FR-7. Политика долговечности.** Конфигурируется через `StoreConfig`:
- `SyncPolicy.NEVER` — только `write`, сброс на усмотрение ОС. Быстро, при отключении питания теряется хвост.
- `SyncPolicy.EVERY_WRITE` — `FileChannel.force(false)` после каждой записи. Медленно, зато `put` вернул управление ⇒ данные на диске.

Значение по умолчанию — `EVERY_WRITE` (безопасное по умолчанию). `BATCHED` (группировка по времени/объёму) отложен на v0.2.

**FR-8. Блокировка файла.** При открытии берётся `FileLock` на файл данных. Попытка открыть тот же файл вторым процессом ОБЯЗАНА завершаться внятным исключением, а не тихой порчей данных.

**FR-9. Версионирование формата.** Файл начинается с заголовка, содержащего магическую сигнатуру и номер версии формата. Открытие файла с чужой сигнатурой или с версией новее известной ОБЯЗАНО завершаться отказом.

## 4. Нефункциональные требования

**NFR-1. Платформа.** Java 25 (Gradle toolchain, не системный JDK). Preview-фичи не используются. Рантайм-зависимостей — ноль; всё стороннее только в `testImplementation`.

**NFR-2. Модель конкурентности.** Много читателей, один писатель — подробности в разделе 5, который является нормативным.

**NFR-3. Гарантии корректности.** Операции над **одним** ключом линеаризуемы. Читатель никогда не наблюдает частично записанное значение. Между разными ключами никакой атомарности не гарантируется. Поток, выполнивший `put`, при последующем `get` ОБЯЗАН увидеть своё значение.

**NFR-4. Память.** Все ключи и метаданные постоянно находятся в куче. Документация ОБЯЗАНА содержать честную оценку накладных расходов на ключ (порядка 80–120 байт при коротких ключах) и вытекающий предел применимости.

**NFR-5. Производительность.** Числовых целей в 0.1 нет — это ловушка преждевременной оптимизации. Требование иное: зафиксировать baseline (операций/с для обеих политик sync) в `docs/journal.md`, чтобы в v0.2 было с чем сравнивать. Строгие замеры на JMH — v0.2.

**NFR-6. Операционные системы.** Linux и macOS — обязательны, зелёные тесты. Windows — best-effort: синхронизация каталога там не работает, соответствующие тесты помечаются `@DisabledOnOs(WINDOWS)`. Отказ от поддержки Windows ОБЯЗАН быть зафиксирован в ADR, а не подразумеваться.

**NFR-7. Обработка ошибок.** `IOException` пробрасывается наружу, не заворачивается в `RuntimeException`. После неустранимой ошибки записи стор переходит в **poisoned state**: все последующие мутирующие вызовы отклоняются немедленно. Тихое продолжение работы после сбоя записи хуже громкого отказа.

**NFR-8. Логирование.** `System.Logger` (JDK), без сторонних фасадов. Уровень INFO — открытие/закрытие/усечение хвоста; DEBUG — не обязателен.

## 5. Модель конкурентности (нормативный раздел)

Этот раздел — сердце проекта. Всё описанное ниже ОБЯЗАНО быть покрыто ADR-0003 и тестами `TR-5`.

**5.1 Схема.**
- Индекс — `ConcurrentHashMap<Key, Loc>`, где `Key` — обёртка над `byte[]` с корректными `equals`/`hashCode`, `Loc` — `record(long offset, int length)`.
- Все записи сериализуются одним `ReentrantLock`. **`synchronized` использовать ЗАПРЕЩЕНО.** Не из-за пришпиливания: начиная с JDK 24 (JEP 491) виртуальный поток, заблокированный внутри `synchronized`, в подавляющем большинстве случаев блокировки на мониторе больше не пришпиливает несущий поток — старое обоснование этого запрета для Java 25 неверно. Причина запрета — другая: `ReentrantLock` даёт явный API (`tryLock`, `tryLock(timeout, unit)`, `isLocked`), которым можно будет диагностировать зависшего писателя и опереться на него при реализации poison state, а выделенное поле-лок делает единственную критическую секцию проекта (весь путь записи, 5.3) видимой при чтении кода вместо неявного монитора на объекте. Дополнительный довод: отсутствие пришпиливания у `synchronized` — деталь реализации конкретной версии JVM, а не гарантия JLS; корректность модели конкурентности не должна зависеть от того, зафиксировано ли это поведение спецификацией языка.
- Чтения выполняются без блокировок позиционным `FileChannel.read(ByteBuffer, position)` — этот метод потокобезопасен и не трогает общую позицию канала.

**5.2 Ключевой инвариант.**
> Байты, единожды записанные по некоторому смещению, никогда не изменяются.

Из него следует безопасность чтения без блокировок: читатель, получивший `Loc` из индекса, прочитает корректные данные, даже если ключ в этот момент перезаписан или удалён (он просто увидит предыдущую версию — допустимый результат для линеаризуемости).

**Инвариант нарушается сжатием.** Это осознанный технический долг: до реализации v0.2 в `docs/concurrency.md` ОБЯЗАНА быть запись о том, что схема чтения потребует пересмотра (подсчёт ссылок на файл либо копирование под защитой блокировки).

**5.3 Порядок операций записи** (нарушать ЗАПРЕЩЕНО):
1. Сформировать буфер записи целиком в памяти.
2. Записать в файл по текущему смещению хвоста.
3. При `SyncPolicy.EVERY_WRITE` — `force(false)`.
4. Только теперь опубликовать `Loc` в индексе.

Публикация в `ConcurrentHashMap` устанавливает отношение happens-before, поэтому читатель, увидевший новый `Loc`, гарантированно увидит и записанные байты.

**5.4 Известная ловушка.** `FileChannel` реализует `InterruptibleChannel`: если поток-читатель будет прерван во время чтения, канал закроется и станет непригоден для **всех** потоков. В 0.1 это ОБЯЗАНО быть задокументировано как ограничение («не прерывайте потоки, работающие со стором»); корректная обработка (переоткрытие канала) — v0.2.

## 6. Формат файла (нормативный раздел)

Порядок байтов — big-endian (значение `ByteBuffer` по умолчанию; выбор фиксируется в ADR-0002, чтобы никто потом не переставил его «для скорости»).

**Заголовок файла, 16 байт, записывается один раз при создании:**

| Поле | Тип | Значение |
|---|---|---|
| magic | 4 байта | ASCII `KVB1` |
| formatVersion | uint16 | `1` |
| flags | uint16 | зарезервировано, `0` |
| reserved | 8 байт | нули |

**Запись:**

| Поле | Тип | Комментарий |
|---|---|---|
| crc32c | uint32 | по всем последующим полям записи |
| timestampMillis | int64 | момент записи; нужен для сжатия |
| flags | uint8 | бит 0 — tombstone |
| keyLength | uint16 | 1…65535 |
| valueLength | uint32 | 0…16 МиБ |
| key | keyLength байт | |
| value | valueLength байт | у tombstone длина 0 |

**Правило восстановления.** Читаем от конца заголовка файла последовательно. Запись принимается, если она целиком помещается в файл и CRC совпал. Первая непринятая запись задаёт точку усечения: `truncate(offsetOfFailedRecord)`. Факт усечения и число отброшенных байт ОБЯЗАНЫ логироваться на уровне INFO.

## 7. Требования к тестированию

**TR-1. Уровни.** Пять уровней, все обязательны для 0.1: модульные, property-based, краш-тесты, тесты конкурентности, тесты на порчу файла.

**TR-2. Property-based (jqwik).** Оракул — обычный `HashMap<Key, byte[]>`. Генерируется случайная последовательность операций (`put`/`get`/`delete`/`reopen`), после каждой сверяется наблюдаемое состояние с оракулом. Операция `reopen` (закрыть и открыть стор заново) ОБЯЗАНА входить в набор — именно она ловит ошибки восстановления.

**TR-3. Краш-тесты.** Дочерняя JVM пишет данные в цикле, родитель убивает её в случайный момент.
- Убийство ОБЯЗАНО выполняться через `Process.destroyForcibly()`. `destroy()` шлёт SIGTERM, отрабатывают shutdown-хуки — тест становится нечестным.
- Проверяется: при `EVERY_WRITE` все подтверждённые записи на месте; при `NEVER` допускается потеря хвоста, но НЕ порча ранее записанного и НЕ падение при открытии.
- 20 итераций в CI, отдельная Gradle-задача на 500+ итераций локально.

**TR-4. Порча файла (fuzz).** Случайный байт в случайной позиции инвертируется. Требование: открытие завершается либо успешно с усечением, либо внятным исключением; данные, расположенные до точки порчи, доступны. Необработанные `BufferUnderflowException`, `NegativeArraySizeException` и `OutOfMemoryError` (последний — от доверия испорченному полю длины) считаются провалом теста.

**TR-5. Конкурентность.** Пул виртуальных потоков: N читателей, M писателей.
- Каждый писатель ведёт свой набор ключей и пишет значения с монотонно растущим счётчиком внутри.
- Читатель проверяет, что прочитанное значение — одно из когда-либо записанных и что счётчик по конкретному ключу не убывает во времени в рамках одного потока.
- Отдельная проверка: `put` с последующим `get` в одном потоке всегда возвращает своё значение.
- Прогон не менее 10 секунд, любое исключение в любом потоке — провал.
- 10 секунд в CI (`slowTest`), отдельная Gradle-задача `concurrencyTestExtended` — 10 минут локально (Definition of Done, раздел 10).

**TR-6. Покрытие.** JaCoCo. Порог 80% строк для пакетов формата и восстановления; для остального порога нет. Покрытие — индикатор, а не цель.

**TR-7. Детерминизм.** Все случайные тесты печатают использованный seed в сообщении об ошибке, чтобы падение воспроизводилось. Временные файлы — только через `@TempDir`.

**TR-8. Разделение по скорости.** Быстрый набор (`./gradlew test`) укладывается в 120 секунд (изначально было 60 — пересмотрено на Этапе 7, когда property-тест TR-2 вырос до 1000 итераций ради Definition of Done и стал занимать большую часть бюджета). Краш-тесты и длительные стресс-тесты — в задаче `./gradlew slowTest`, тег JUnit `slow`.

**TR-9. Стретч-цели** (не блокируют 0.1): PIT для мутационного тестирования, Lincheck для формальной проверки линеаризуемости.

## 8. Сборка и инфраструктура

- **Gradle**, Kotlin DSL, wrapper закоммичен в репозиторий. Версии библиотек — в `gradle/libs.versions.toml` (version catalog).
- `java { toolchain { languageVersion = JavaLanguageVersion.of(25) } }` — сборка не зависит от JDK на машине.
- Тестовые зависимости: JUnit 5, AssertJ, jqwik.
- Задачи: `test`, `slowTest`, `jacocoTestReport`, `javadoc`.
- **CI** (GitHub Actions): матрица ubuntu-latest + macos-latest, Temurin 25, запуск `test` на каждый push и `slowTest` по расписанию.
- Форматирование: Spotless с `palantir-java-format`, проверка в CI. Ставится один раз и снимает целый класс споров с самим собой.
- Файлы репозитория: `LICENSE` (MIT), `.gitignore`, `.editorconfig`, `CHANGELOG.md` в формате Keep a Changelog.

## 9. Документация

| Документ | Назначение |
|---|---|
| `README.md` | Что это, зачем, как собрать и запустить, явная пометка «учебный проект» |
| `docs/adr/` | Архитектурные решения в формате MADR, файлы `NNNN-краткое-название.md` |
| `docs/format.md` | Спецификация формата (раздел 6, вынесенный отдельно и поддерживаемый в актуальном состоянии) |
| `docs/concurrency.md` | Модель конкурентности, инварианты, известные ограничения |
| `docs/testing.md` | Стратегия тестирования: что каким уровнем проверяется и почему |
| `docs/journal.md` | Лабораторный журнал: гипотезы, замеры, что сломалось и почему |
| `CHANGELOG.md` | История версий |

**Правила ведения ADR:**
- ADR пишется **до** реализации решения и попадает в тот же коммит/PR, что и код.
- Статусы: `Proposed` → `Accepted` → `Superseded by ADR-NNNN`. Принятый ADR не редактируется по существу — вместо этого пишется новый, отменяющий старый.
- Обязательный раздел «Рассмотренные альтернативы» с причиной отказа. ADR без альтернатив бесполезен.

**ADR, обязательные для 0.1:**
- ADR-0001 — лог-структурированная модель Bitcask (альтернативы: B-tree, LSM, сериализация всей карты)
- ADR-0002 — формат записи, CRC32C, порядок байтов
- ADR-0003 — модель конкурентности: один писатель, читатели без блокировок
- ADR-0004 — политика долговечности и значение по умолчанию
- ADR-0005 — отказ от `MappedByteBuffer` и от FFM API в пользу `FileChannel`

Для учебного проекта `docs/journal.md` — самый ценный файл. Именно там окажется всё, ради чего проект затевался: «предполагал X, замерил Y, объяснение — Z».

## 11. План на два вечера

**Вечер 1 (3–4 часа).** Каркас Gradle с version catalog и CI. Класс `Key`, `StoreConfig`, интерфейс. Формат записи, сериализация/десериализация с отдельными unit-тестами. `put`/`get`/`delete` в один поток, восстановление индекса. Property-тест с оракулом. ADR-0001, ADR-0002.

**Вечер 2 (3–4 часа).** CRC32C и усечение хвоста. `SyncPolicy`. `ReentrantLock` + `ConcurrentHashMap`, `FileLock`, poisoned state. Краш-тест и тест конкурентности. ADR-0003, ADR-0004, ADR-0005. README, journal с первым замером.

**Порядок отказа при нехватке времени** (жертвуем сверху вниз): Spotless → порог JaCoCo → fuzz-тест `TR-4` → macOS в матрице CI → `FileLock`. Ниже этой черты резать нельзя: краш-тест и тест конкурентности — то, ради чего всё затевалось.

## 12. Риски и открытые вопросы

- **R-1.** Два вечера — оптимистичная оценка при полном объёме раздела 10. Наиболее вероятный исход: ядро и property-тесты за два вечера, краш- и concurrency-тесты плюс ADR — третий вечер. Планировать стоит три, радоваться — если хватит двух.
- **R-2.** Краш-тесты нестабильны в CI (таймауты, различия файловых систем). Смягчение: малое число итераций в CI, основной объём — локально.
- **OQ-1.** Копирование входных массивов при каждом `put` — сколько это стоит? Измерить в v0.2, при необходимости вынести в опцию `unsafeNoCopy`.
- **OQ-2.** Как сжатие уживётся с чтением без блокировок — главный архитектурный вопрос v0.2. Решение ОБЯЗАНО быть оформлено как ADR до начала работы над сжатием.
- **OQ-3.** Нужен ли собственный `Key` или достаточно `ByteBuffer.wrap` (у него value-семантика `equals`/`hashCode`). Сравнить по памяти в v0.2.
